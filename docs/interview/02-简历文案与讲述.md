# EdgeVision 简历文案与项目讲述
适用方向：Linux 音视频 / 边缘 AI 应用。项目日期请填真实开发区间，不用本次提交日期反推项目持续时间。以下表述对应仓库实现；只有能独立解释和复现的部分，才写成自己的熟练能力。

## 1. 推荐简历版本
**EdgeVision：基于 RK3568 的视频感知与事件录像系统｜个人项目｜[真实起止时间]**

基于 C++17/Linux，构建 V4L2 采集、YOLOv5 NPU 推理、MPP H.264 编码、RTSP 预览和 ROI 事件录像链路，支持远程状态查询、异步抓拍及推理控制。

- 设计固定容量帧池与独立有界队列，以只读帧引用管理跨线程生命周期；推理采用最新帧消费和结果有效期控制，降低慢推理导致的旧帧积压，保持视频分支独立运行。
- 完成 YOLOv5 Letterbox、anchor 解码及 NMS，接入原生量化输出；在同一 640×480 输入、30 Hz 回放且编码开启的单轮 60 秒对照中，检测吞吐由 11.74 提升至 14.59 FPS，检测链 P95 由 157.68 降至 135.19 ms。
- 基于 GStreamer/MPP 构建 H.264 编码与 RTSP 服务，实现按 GOP 保存的事件预录缓存、尾随延长和录像清单；输入断流与摄像头重启时收尾旧事件，并提供录像状态查询。
- 基于 epoll/eventfd/timerfd 接入控制与指标采集，增加慢推理降级、滞回恢复及过期结果抑制；通过板端延迟注入验证降级期间采集、编码和抓拍继续工作，以及撤销延迟后的恢复。

技术栈：C++17、Linux、V4L2、RKNN、GStreamer/MPP、RTSP、OpenCV、epoll、多线程。

若简历版面紧张，保留前 3 条，将第 4 条的故障验证压缩进第 1 条。无需把所有库和线程概念都堆到技术栈。

## 2. 偏 Linux 音视频岗位的替换重点
可将项目描述后的第一条换成：
“封装 V4L2 非阻塞采集，处理协商尺寸、stride 和有效字节校验；复制有效图像行后及时归还驱动缓冲，使用固定容量帧池承接推理、视频和抓拍分支。”

把视频链路放在第二条、推理优化放在第三条。MPP 应表述为硬件编码插件接入；RGA 只作为有对照实验的备选方案，不写成默认性能收益来源。当前没有音频链路，音画同步不能作为已实现能力。

## 3. 偏边缘 AI 应用岗位的替换重点
把模型正确性与量化输出优化置于第一条，并强调：
“校验输出布局及 logits 语义，固定输入交替对照浮点和原生量化输出，验证检测框、类别与置信度一致；将推理耗时拆为输入、执行、输出及后处理，区分模型执行与系统吞吐瓶颈。”

不要把调用已转换的 RKNN 模型写成训练模型、自研推理框架或实现模型量化算法。原生量化输出优化发生在运行时输出获取与后处理路径。

## 4. 60～90 秒项目介绍
“这个项目是在 RK3568 上做视频感知和事件录像。基础链路是摄像头采集、YOLOv5 推理、H.264 编码和 RTSP 预览，检测到 ROI 内人员后保存事件视频。

我重点解决的是这些模块同时工作时的时效和异常处理。比如摄像头实采约 20 帧，但当前完整推理只能处理约 14 帧，如果旧帧一直排队，检测结果就会越来越滞后。所以我用固定容量帧池和独立队列，推理只取最新帧，并过滤过期结果，视频不用等检测。

性能上，我发现不能只看 NPU 的执行时间，还要看输出获取和后处理。改成原生量化输出后，在同输入、编码开启的 60 秒对照里，检测从 11.74 到 14.59 FPS。RGA 的备选路径在这个分辨率下反而更慢，所以没有强行使用。

稳定性上补了慢推理降级、恢复滞回、录像断流收尾和状态查询，并通过板端延迟注入验证。现在还没有做到真实 NPU 卡死后的自动进程恢复，这会是下一步的重点。”

上述口述需结合自己实际参与和理解调整，不要背下文案后把不能解释的工作归为独立完成。

## 5. 三分钟展开顺序
1. 场景与预算：视频流持续输出，推理允许跳帧，事件必须能追溯。
2. 架构：画出帧池与推理/视频/抓拍分支，说明所有权与队列策略。
3. 一个性能问题：先讲输出模式对照，再讲检测 FPS 与 NPU FPS 的区别。
4. 一个稳定性问题：讲过期帧/代际号，或录像无新包时无法收尾的修复。
5. 验证与边界：展示配置、报告、故障注入结果，再解释真实卡死为什么需要子进程。

## 6. 数据怎么说才准确
| 可使用的数据 | 必须同时说明的条件 |
| --- | --- |
| 11.74 → 14.59 FPS，约 +24.3% | 同一固定帧、30 Hz 回放、编码开启、各 60 秒、单轮对照 |
| 157.68 → 135.19 ms P95 | 采集完成到检测完成，不是外部播放延迟 |
| 实采约 20 FPS、检测约 14.4 FPS、P95 约 119 ms | 用户近期短窗口日志，非 24 小时压力测试 |
| 11 项基础验收与 9 项新增验收 | 不同测试集，不能将其相加为互不重叠的故障种类 |
| 退出约 0.22 秒 | 本次可返回调用场景，不承诺驱动卡死时退出上限 |

两组实验的输入节奏和代码阶段不同，不能把 157.68 ms 与近期 118.60 ms 直接算作严格 A/B 优化比例。

## 7. 不应写入当前简历的说法
- “自研摄像头内核驱动”：目前是 V4L2 用户态封装。
- “DMA-BUF 全链路零拷贝”：目前仍有帧复制和格式转换。
- “RGA 显著加速”：当前对照未显示收益。
- “NPU 提速 24%”：提升来自整体输出路径，不是 NPU 执行本体。
- “30 FPS 实时检测”：30 FPS 是固定回放视频能力，检测约 14.6 FPS。
- “完善的自动故障恢复”：真实 RKNN 永久阻塞和编码器重建尚未闭环。
- “检测精度无损 / 达到某 mAP”：只有固定帧正确性对照。
- “支持音画同步、多摄像头和高并发”：没有相应实现与验收证据。

个人项目和实习经历分开写。本次材料不为实习补造驱动开发、业务规模或工作时长。
